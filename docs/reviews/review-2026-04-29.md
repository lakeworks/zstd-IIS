## Findings

### V-1 — Code does not enforce the hard ceiling at level 17; doc claims "do not raise above 117" but compiled plugin accepts up to level 22

**Type**: rule-impl contradiction (CRIT-3 partially addressed)

**Files**: src/zstd.c:74, CLAUDE.md:83-88

**Observation**: 

Gate-1's adversarial review (CRIT-3) identified that zstd levels 18+ allocate multi-GB per CCtx (chainLog≥28, hashLog≥27), and with the streaming IIS compression API, these cannot be downsized because srcSize is never pledged. At level 22, each concurrent request can attempt a ~2.5 GB allocation, crashing w3wp.exe and taking down all co-tenant sites.

The review recommended three fix options, one of which was "at minimum, remove 122 from the CLAUDE.md table" and "replace with a hard ceiling note at 117."

CLAUDE.md was correctly updated in commit 39ba3f7 to replace the table's 122 | 22 | maximum (very slow) row with 117 | 17 | hard ceiling — see below, and a detailed explanation was added (lines 87-88) stating: "**Hard ceiling at level 17 (= IIS config 117).** ... **Do not raise above 117 without first plumbing ZSTD_c_chainLog / ZSTD_c_hashLog overrides in src/zstd.c.**"

However, the code at src/zstd.c:74 still contains:
`c
if (comp_lev < -5 || comp_lev > ZSTD_maxCLevel())
    return E_INVALIDARG;
`

ZSTD_maxCLevel() returns ZSTD_MAX_CLEVEL, which is 22 per zstd 1.5.7. This means the code accepts any comp_lev up to 22, which translates to IIS config values up to 122. An operator can still configure dynamicCompressionLevel="122" or staticCompressionLevel="122" and the code will accept it, allocating multi-GB and risking the OOM crash CRIT-3 described.

The CLAUDE.md documentation now explicitly warns against this, but the code does not enforce it. This is a silent partial-close: the doc was updated to document the hazard, but the runtime protection was not implemented.

**Recommendation**: Implement one of the three options from gate-1/CRIT-3:
1. **Enforce ceiling at 17 in code**: change the bounds check to if (comp_lev < -5 || comp_lev > 17). This prevents the multi-GB allocation even if CLAUDE.md is ignored.
2. **Adjust chainLog/hashLog**: add ZSTD_CCtx_setParameter(cctx, ZSTD_c_chainLog, 23) and ZSTD_c_hashLog, 22) to cap working memory regardless of level.
3. **Document as known limitation**: if the code is intentionally not restricting the ceiling (deferred for future work), CLAUDE.md should say "the code currently accepts up to level 22; operators configuring above 17 accept the multi-GB memory risk" — but this is not what the current doc says; it says "do not raise above 117 without first plumbing."

The current state (doc warning + code accepting) is a mismatch.

**Priority**: critical
